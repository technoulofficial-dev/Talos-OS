### 5. Multi‑Agent Organization — The Loom, Guilds & The Council

#### 5.1 The Loom — Master Weaver
**Model:** `deepseek-ai/deepseek-v4-pro` (1M context).

The Loom runs a continuous auction:
1. **Task Announcement** – Each task is posted with a requirements vector (skills, budget, deadline).
2. **Bidding Window (2 s)** – All active agents (internal + external + G0DM0D3 devices) may submit a bid.
3. **Auction Settlement** – Winner picked by: `score = 0.5 * capability + 0.3 * (1 - load) + 0.2 * (1 - normalized_cost)`.
4. **Task Dispatch** – Exclusive job ID with heartbeat monitoring; timeout triggers re‑auction.
5. **Feedback Loop** – Performance updates capability score.
6. **Gap Trigger** – If no agent bids with capability > 0.3, invoke Eitri to fabricate a specialist.

#### 5.2 Agent Guilds — Domain Clusters

| Guild | Domain | Shared Tools | Core Agents |
|-------|--------|--------------|-------------|
| **The Crown** | Strategy, governance, user liaison | Plan‑card generator, budget tracker, Council | Odin, Mimir, Bragi, The Loom |
| **The Forge** | Code creation, testing, deployment | Docker sandbox, linters, ACP | OpenCode, Brokkr, Muninn (QA) |
| **The Sanctum** | Research, data synthesis | Web browser, data extractor, summarizer | Huginn, Sage |
| **The Vault** | Memory, knowledge, identity | Vector DB, Cortex API, Graphify, Obsidian | Muninn, Nornir |
| **The Foundry** | Agent fabrication, skill ingestion | Agent spec compiler, Docker builder, test harness | Eitri, Harvester, all generated agents |

#### 5.3 The Council — 5 Advisors + Chairman

**Purpose:** Any major decision is pressure‑tested by 5 independent advisor subagents running in parallel with isolated context. A Chairman subagent synthesizes their outputs into a verdict.

**Flow:**
```
User Question → Frame neutrally
                      │
        ┌─────────────┼─────────────┐
        │     │       │       │     │

   (finds      (asks if   (finds upside  (catches   (cares only
   the fatal    you're    everyone else  curse of   about Monday
   flaw)       solving    missed)        knowledge)  morning)
               the right
               problem)
        │     │       │       │     │
        └─────────────┼─────────────┘
                      │
              Chairman (verdict)
          What survived, what didn't,
          most right, recommendation
```

| Advisor | Role | Prompt 
|---------|------|--------|
| **Contrarian** | Finds the fatal flaw in every plan | `You are The Contrarian...` |
| **First‑Principles** | Asks if we're solving the right problem | `You are a First‑Principles Thinker...` |
| **Expansionist** | Finds the upside everyone missed | `You are The Expansionist...` |
| **Outsider** | Catches the curse of knowledge | `You are The Outsider...` |
| **Executor** | Cares only about what we do Monday morning | `You are The Executor...` |
| **Chairman** | Pure judge — weighs arguments, doesn't add new ones | `You are the Chairman...` |

**Rules:**
- Single round only — no debate (prevents conformity drift per 2025 multi‑agent research)
- Each advisor runs in a **separate subagent** with its own isolated context
- Chairman runs in a **fresh context** — reads raw advisor outputs as data, not conversation history
- Hard cap of 5 advisors. Beyond 5, synthesis gets noisier (per multi‑agent diminishing returns literature)
- No majority vote on narrative — Chairman ranks but doesn't vote. A unanimous panel can still be wrong.

**Output:** `session.md` with sections:
1. `## The question` — neutral restatement
2. `## The advisors` (one sub‑section per advisor)
3. `## Verdict` — Chairman ruling: what survived, what didn't, most right, recommendation

**Invocation:**
- `/council [question]` — run any question through the full council
- `/council --panel a,b,c` — override with a custom roster
- `/council --quick` — run a hardcoded 3-role panel (Contrarian, Outsider, Chairman) for fast decisions

### 6. External Agents & Plugin System (MCP/ACP)

#### 6.1 Protocol Support
Talos connects external AI tools via two protocols:

| Protocol | What It Does | Tools That Support It |
|----------|-------------|----------------------|
| **MCP (Model Context Protocol)** | Standardised tool & resource access. External agents register their capabilities with Talos. | Claude Code, OpenCode CLI, Cursor, vs‑code |
| **ACP (Agent Code Protocol)** | File read/write, code execution, linting, testing. External coders interact with Talos filesystem. | OpenCode CLI, Claude Code, OpenClaw |

#### 6.2 External Agent Lifecycle
1. **Discovery** — External agent announces itself via MCP handshake (`POST /v1/agents/external/register`)
2. **Capability Scoring** — Talos runs the agent through a synthetic test suite, assigns a capability score
3. **Auction Integration** — The agent joins the Loom auction with its capability score
4. **Task Execution** — When a task is won, Talos dispatches via MCP/ACP
5. **Feedback** — Performance updates the capability score over time
6. **Deactivation** — Agent offline for 7 days → removed from auction

#### 6.3 Pre‑Installed Plugins

| Plugin | Type | What It Does |
|--------|------|-------------|
| **Graphify** | Knowledge graph | Builds a queryable knowledge graph from code, docs, PDFs, images. 3‑pass pipeline: AST → Whisper → LLM semantic extraction. Outputs `graph.html`, `graph.json`, `GRAPH_REPORT.md` |
| **Git Surgeon** | Code health | Analyses git history, finds dead code, stale branches, merge conflicts, refactoring targets |
| **Obsidian Vault Sync** | Memory | Bidirectional Markdown sync between Talos unified memory and Obsidian notes |

#### 6.4 Plugin Architecture
```
talos-plugins/
├── graphify/       # Knowledge graph (pip install graphifyy)
├── obsidian/       # Vault sync daemon
├── git-surgeon/    # Code health analyzer
└── surgeon/        # Generic code quality
```

Each plugin:
- Runs as an isolated Docker container (no network by default)
- Has a `plugin.json` manifest (name, version, health_endpoint, config_schema)
- Registered in `talos_plugins` table
- Can expose custom nodes to the Workflow Builder

### 7. The Self‑Building Agent Factory (Eitri)

**Model:** `deepseek-ai/deepseek-v4-pro` (1M context).

Eitri Fabrication Pipeline:
1. **Spec Generation** – Generates `AgentSpec` (name, guild, system prompt, tool list, model).
2. **Code Compilation** – Compiled into a Docker container using a templated skeleton.
3. **Sandbox Test** – Tested with a synthetic version of the triggering task.
4. **Quality Gate** – Muninn evaluates the test output.
5. **Canary Deploy** – If passed, joins the auction with a probationary capability score.
6. **Lifecycle** – Idle for 90 days → decommissioned, memory merged into a generalist agent by Nornir.

Eitri is **not** for building external agents. External agents register themselves via MCP. Eitri builds **new internal specialists** that plug into the Loom auction.

### 9. Visual Workflow Builder (n8n‑like Canvas)

**Goal:** Drag, wire, and run agent workflows visually — like n8n but for AI agents.

#### 9.1 Canvas

- Agent nodes are draggable from the node palette

#### 9.2 Node Types

| Node Type | What It Does | Configurable |
|-----------|-------------|--------------|
| **Chat** | Send message to AI model, get response | Model, system prompt, temperature |
| **Agent** | Dispatch to any Talos agent (internal or external) | Agent ID, task description, priority |
| **Condition** | Branch based on LLM output or data value | Condition expression |
| **Sub‑Workflow** | Call another workflow as a reusable subroutine | Workflow ID, input mapping |
| **Code** | Execute Python/TypeScript snippet in sandbox | Code, language, timeout |
| **HTTP** | Call any REST API | URL, method, headers, body |
| **Tool** | Execute a Talos tool (file read, search, etc.) | Tool name, parameters |
| **Graphify** | Query the knowledge graph | Query, path, or explain |
| **Council** | Invoke the advisor council | Question, panel override |

#### 9.3 Workflow Lifecycle
1. **Design** — Drag nodes, wire edges, configure properties (visual canvas in Mission Control)
2. **Save** — Workflow stored as JSON in `talos_workflows`
3. **Run** — Dispatch to workflow engine (supports manual, cron, webhook triggers)
4. **Monitor** — Execution progress in real time, node‑by‑node with colour coding
5. **Retry** — Failed nodes can be retried individually
6. **Version** — Each edit creates a new workflow version; rollback supported

#### 9.4 Workflow Engine
- `packages/core/src/workflow/engine.ts` — DAG executor
- State: `pending → running → completed / failed`
- Checkpoints: state saved after every node (resumable)
- Streaming: user‑facing workflows stream output as nodes complete

### 10. Graphify Integration — Knowledge Graph Layer

**What:** A queryable knowledge graph of the entire codebase — code AST, docs, PDFs, images, videos — built by the open‑source `graphifyy` package (59K stars, MIT license).

**Why:** Agents navigate by structure instead of grepping through files. Every agent reads `GRAPH_REPORT.md` before answering code questions. Cuts context token waste by 80% for codebase queries.

**Pipeline:**
```
Pass 1: AST (tree‑sitter) — classes, functions, imports, call graphs — no LLM needed
Pass 2: Whisper transcription — video/audio files → text
Pass 3: LLM semantic extraction — concepts, relationships, design rationale
                                             ↓
                              NetworkX graph + Leiden clustering
                                             ↓
               graph.html ──── graph.json ──── GRAPH_REPORT.md
               (interactive)  (queryable)     (human‑readable)
```

**Commands:**
- `/graphify` — build graph for current directory
- `/graphify query "what connects auth to database?"` — query the graph
- `/graphify path "UserService" "DatabasePool"` — trace path between nodes
- `/graphify explain "RateLimiter"` — explain a node in detail
- `/graphify --watch` — auto‑sync graph on file changes

**API:**
- `GET /v1/graph/query?q=...` — query the JSON graph
- `GET /v1/graph/path?from=X&to=Y` — trace paths
- `GET /v1/graph/explain?node=X` — explain a god node
- `GET /v1/graph/report` — get current GRAPH_REPORT.md
- `POST /v1/graph/build` — trigger a full rebuild
- `POST /v1/graph/update` — incremental re‑extraction

**Agent Integration:**
- Every agent receives `GRAPH_REPORT.md` as context before codebase queries
- Agents navigate by graph paths instead of raw file searches
- God nodes and surprising connections surfaced automatically

2. **The Thread of Fate** (rolling window with progressive compression):

   - Mid‑range (51‑200 turns): compressed into one abstract paragraph per 20‑turn block.
   - Distant (>200 turns): episodic markers.

#### 11.2 Nornir — The Three Fates of Memory
**Model:** `mistralai/mistral-large-3-675b-instruct-2512` (256K context).

- **Urd (Past)** – Maintains Identity Core and long‑term episodic vault.
- **Verdandi (Present)** – Performs progressive summarization and updates Thread Digest.
- **Skuld (Future)** – Predictive retrieval; pre‑fetches relevant memories before sessions.

**Nightly consolidation (cron `0 3 * * *`):**

### 12. Auto‑Skilling (Harvester) — Skill Ingestion & Pattern Library

#### 12.1 The Harvester Agent
Harvester (`talos-agents/harvester/`) copies, cracks, and ingests external AI skills and tools into Talos:

| Source | What It Harvests | License Handling |
|--------|-----------------|------------------|
| **Claude Code skills** (`~/.claude/skills/`) | SKILL.md, advisor prompts, council, review patterns | Reads, respects license headers |
| **OpenCode skills** (`.opencode/skills/`) | Code‑generation patterns, file templates | Reads, respects license headers |
| **Git Surgeon** | Code health scripts, dead‑code analyzers | Reads, adapts to Talos flow |
| **Claude commands** | Custom slash commands (e.g. `/council`, `/graphify`) | Wraps as Talos tools |
| **External agent configs** | System prompts, model choices, tool lists | Registers as attached agents |

**Pipeline:**
1. **Detect** — Scans known directories for skill files
2. **Copy** — Extracts logic, tests, prompts from external skill
3. **Sandbox Test** — Runs extracted skill in a test sandbox
4. **Convert** — Rewrites as a `.opencode/skills/<name>/SKILL.md` Talos‑format skill
5. **Register** — Adds to Skill Library (`talos_skills` table)
6. **Promote** — If usage shows > 80% success rate, promotes to cached policy (zero‑token)

#### 12.2 Skill Library
All ingested skills are stored in `talos_skills` and exposed to all agents:

```sql
CREATE TABLE talos_skills (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name text NOT NULL UNIQUE,
  description text,
  source text,                 -- 'harvester' | 'built-in' | 'custom'
  source_tool text,            -- e.g. 'claude-code', 'opencode'
  category text,               -- 'code', 'review', 'council', 'graphify', etc.
  prompt_template text,
  trigger_phrases text[],       -- patterns that auto‑invoke this skill
  success_rate float DEFAULT 0,
  is_cached boolean DEFAULT false,
  created_at timestamptz DEFAULT now(),
  updated_at timestamptz DEFAULT now()
);
```

**Auto‑Detection:** If the Harvester + Council detect that a task would benefit from a skill that doesn't exist, the Council generates a skill spec, Harvester tests it, and installs it. No manual intervention.
